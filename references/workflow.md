# 工作流与协作纪律（DIS 卡等项目实战沉淀）

来源：DIS 聊天模拟器卡项目（作者本机项目，未随仓库发布）全程实战教训。这些是文档里没有、只有踩过才知道的。

## 一、构建链纪律

1. **构建命令绝不用管道接 grep 过滤输出**。`python tools/build_dc.py 2>&1 | grep -E "..."` 会掩盖构建崩溃——grep 匹配到旧输出的关键字就返回 0，链条继续跑，旧 dist 被当成新文件交付（真实发生过，用户收到的文件是旧内容）。
   正确做法：构建脚本单独跑，`tail -3` 看完整输出，确认"已写出"行真的出现。
2. **交付前 grep 交付文件本身**，验证本次新增内容的关键词真的在里面（比如新角色名、新规则编号）。不验证不交付。
3. **单条门禁**：replaceString 上限 20000，构建脚本里通常设有更保守的内部阈值（DIS 项目 MAX_RULE=17980）。每个 js 文件一条规则，加代码前先量体积余量（剥注释后算）；超了就挪到有余量的文件，别硬塞。
4. 一次只改一处、只测一条链路；三次修不好就停止局部修补，全面重查。

## 二、文风纪律（persona / 世界书 / 开场白）

1. persona 和世界书是**给 AI 看的行为手册**：短指令、无形容词堆砌、无歧义、标点精简。用户明确讨厌"文学腔"和"AI 刻板话"（例："有商业嗅觉"、"口嫌体直正"这种标签式评语不要写）。
2. **现实背景是底料不是台词**：用户提供的真人现实信息（职业、家境、病情）用于让角色生动，角色在网上不会主动把这些挂嘴边。写成发言内容=翻车（阳岚"商业嗅觉"事件、凛堂光"躯体化"标签事件）。
3. 标点符号能省就省，大于号小于号这类装饰性格式符对 AI 阅读没有帮助，还占字数。
4. 开场剧情要"像群友嬉戏打闹"，不是作者旁白；每条消息时间错开、按时间顺序排列。
5. 开场白有专门的社区协议（3200–3800 字、第三人称、对白≥40%、活人感条款），原文与嵌入注意见 [opening-protocol.md](opening-protocol.md)。

## 三、关系网纪律（群像卡最重要）

1. **不乱加人际关系**：只写用户明确说过的关系。用户没说"A 和 B 关系好"，就不写。
2. **删关系 = 整段删除**。绝不写"他们关系一般/不熟"这种否定句——否定句等于新设定，AI 会拿去演。用户原话："谁和谁关系其实一般，是让你把原来写错的关系直接删掉，不是让你强调他们关系一般"。
3. 改人设用"替换性质"不用"否定描述"：例，用户说"小魅不知道所有人的秘密"，正确写法是"她不在乎其他人的秘密"，错误写法是"小魅不知道所有人的秘密"。
4. 性别、名字以用户最新口径为准，全局替换后要全文 grep 复核旧名残留（苏妍雅→苏雅妍、咬窈不疼→芒舒窈两次改名都是全链路替换：世界框架+世界书+代码+开场剧情）。

## 四、解析格式约定（构建脚本依赖，别擅自改）

- 花名册章节标题用正则 `【[^】]*(?:角色花名册|群友人设)】` 匹配（用户会自己改章节名）
- 花名册行格式：`- 名字：一句话`（全角冒号）
- 表情列表必须是 persona 最后一段
- 改动这些格式前必须同步改构建脚本的解析正则，两边一起验证

## 五、平台机制实战备忘

- `{{hud}}` 是平台功能栏占位符：不接 HUD 的卡要巡检清掉字面文本，否则玩家看到原始标记
- flex 容器滚动区必须 `min-height:0`，否则溢出内容被裁剪
- 在线状态散列算法要加乘法+异或混合：简单多项式散列会让某些角色 23/24 小时离线
- 存档丢失时从平台历史消息的【名字：X】标记认回玩家身份（开局"已有账号"功能靠这个，不是骗人的）
- 开局创建页："已有账号"和"随便看看"应共用直接进入逻辑；AI 必须记住已注册的玩家角色，别把玩家当成新捏的网友

## 六、交付纪律

1. **文件名必须带日期或版本戳**（如 `①正则代码-导入创卡页_1011.json`）。用户明确抱怨过同名文件分不清新旧。旧版挪进备份子文件夹，不删不覆盖。
2. 每次交付说明：改了什么、验证方式、文件路径。
3. 不声称未经实际执行的运行结果已验证。
4. 交付物默认进当前工作区或用户指定目录，复制到桌面交付文件夹时确认落点。
